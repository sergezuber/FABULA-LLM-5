# Вклад в FABULA-LLM-5

[English](CONTRIBUTING.md) · [中文](CONTRIBUTING.zh-CN.md) · [Русский](CONTRIBUTING.ru.md)

Спасибо за интерес! Этот проект — local-first обвязка автономного агента: именно слой надзора — гейты верификации, чекпоинты, защиты от зацикливания, квитанции — заставляет любую модель в сокете выдавать верифицированную работу. Особенно приветствуются изменения, которые сохраняют её работу **полностью офлайн на обычном железе**.

## Основные правила

- **Один плагин = один файл = один экспорт.** Каждый `plugin/fabula-*.ts` экспортирует ровно одну фабрику `Fabula*` и ничего больше — движок вызывает *каждый* экспорт файла плагина как плагин, поэтому случайный экспорт вспомогательной функции ломает загрузку. Общие хелперы живут в `plugin/lib/`.
- **Манифест — закон.** Каждый новый инструмент, плагин или внешняя зависимость должны быть объявлены в `plugin/lib/manifest.ts` (с командами `check` и `install`) — после чего пересоберите сводку: `bun scripts/install-deps.ts --md > DEPENDENCIES.md`. Добавьте локализованные имя и описание плагина плюс теги возможностей в `plugin/lib/i18n.ts` (теги используют тот же словарь, что и таблица плагинов в README).
- **Документация едет вместе с кодом.** Возможность, не отражённая в `README.md` / `docs/` в том же PR, считается незавершённой.
- **Секреты никогда не попадают в репозиторий.** Ключи живут только в `.env` / `*.key` (в gitignore). Шаблоны (`.env.example`, `fabula.config.example.json`) содержат только заглушки.

## Тестирование

Зелёный `bun test` может скрывать плагин, который не грузится в живой обвязке, — юнит-тесты необходимы, но недостаточны.

Наборов тестов **три**, и каждый покрывает слой, до которого не дотягиваются остальные. Правка в адаптере
или в движке не проверяется набором плагинов, каким бы зелёным он ни был, — именно из-за этого разрыва пять
файлов тестов адаптера давали ноль тестов, пока `pytest -q` рапортовал об успехе.

```bash
cd plugin  && bun install && bun test                       # plugins: unit + corner + wiring
cd proxy   && python3 -m pytest -q                          # the :1235 adapter (watchdogs, admission, framing)
cd engine/packages/opencode && bun typecheck && bun test test/session test/task test/tool
```

Затем проверьте на **настоящем изолированном движке**:

```bash
ISO=$(mktemp -d)
XDG_DATA_HOME="$ISO" fabula serve --port 5099 --hostname 127.0.0.1 &
# check the log for 0 ERROR / failed-to-load lines, and that models/providers appear
```

Гоняйте новые инструменты через их настоящий `execute()` на живых бэкендах. «Выглядит правильно» — это не верификация.

## Пул-реквесты

- Держите PR сфокусированными; объясняйте *почему*, а не только *что*.
- Следуйте стилю окружающего кода (включая плотность комментариев).
- Если правка затрагивает приложение для macOS, пересоберите его командой `./build.sh` из корня репозитория (фронтенд, бинарь движка и бандл приложения — один только `app/build.sh` оставит приложение с устаревшим движком), затем запустите `bash scripts/verify-deploy.sh` и укажите, что именно вы прокликали для проверки.

## Сообщения об ошибках

Заведите issue и укажите: что вы запускали, чего ожидали, что произошло, хвост лога движка и вашу конфигурацию (версия macOS, модель, локально/облако). По всему, что связано с безопасностью, см. [SECURITY.ru.md](SECURITY.ru.md).
