# FABULA-LLM-5 — обзор архитектуры

[English](ARCHITECTURE.md) · [中文](ARCHITECTURE.zh-CN.md) · [Русский](ARCHITECTURE.ru.md)

FABULA-LLM-5 — **автономный агент для программирования на macOS, локальный по умолчанию**.
Генерацию кода, исследовательские задачи и автоматизацию он выполняет на **локальных
моделях** (через LM Studio); тяжёлую работу можно передать облачному провайдеру, но
только явно включив эту возможность. Всё упаковано в нативный `.app`: продукт выглядит и ведёт себя
как полноценное настольное приложение, а не как вкладка браузера.

### 1.1 Движок (`fabula`)

**Движок FABULA** (CLI: `fabula`; развитие стороннего движка — см. [CREDITS](CREDITS.ru.md))
владеет циклом агента: сборкой промпта, диспетчеризацией инструментов, хранилищем
чат-сессий, веб-интерфейсом и рантаймом плагинов. Всё поведение агента настраивается через
`fabula.config.json` — это имя конфиг-файла движка (контракт уровня движка, сохранён ради
совместимости). Рабочий конфиг получается копированием
`fabula.config.example.json` → `fabula.config.json` и заполнением.

### 1.2 Модели — локальные по умолчанию, через адаптер `:1235`

Модели обслуживает **локальный LM Studio**; его собственный порт — `localhost:1234`, но инференс туда из
FABULA не ходит вообще. Каждый инференс-запрос идёт в адаптер на `:1235`; «сырой» порт читается только
ради нативного API метаданных (`/api/v0/models`) — адаптер его не проксирует, и это не инференс.
`LMSTUDIO_URL` переопределяет endpoint инференса; оставляйте её пустой, если только не указываете на
адаптер другой машины. Значение `:1234` молча выключает трансляцию запросов, барьер допуска, оба
сторожевых таймера и ограничитель вывода — и при этом громко не падает, потому что `:1234` отвечает 200
на обычный чат-вызов.
Агентная оболочка **не** говорит с LM Studio напрямую. Она обращается к небольшому
**адаптеру совместимости** на Python — `localhost:1235` (`proxy/lmstudio-adapter.py`). Тот
проксирует запросы в LM Studio и делает следующее, чтобы *структурированный вывод* и *вызовы
инструментов* работали надёжно — а конкурентность, зависания и сбросы кэша управлялись в
одной точке, через которую проходит каждый запрос:

1. **`json_object` → `json_schema`.** Vercel AI SDK (внутри движка) для `generateObject` шлёт
   устаревший режим OpenAI `response_format: {type:"json_object"}`. LM Studio отвечает на него
   **HTTP 400** — он принимает только `json_schema` или `text`. Адаптер переписывает запрос в
   **разрешительный** `{type:"json_schema", json_schema:{…, additionalProperties:true}}`: каждый
   структурированный вызов получает валидный JSON *своей собственной* формы (схема конкретного
   вызова живёт в промпте, а не в теле запроса). Кому нужна строгая грамматика — тот включает её
   заголовком `X-Fabula-Schema` (так судья цели фиксирует форму своего вердикта).

2. **`reasoning_content` → `content`.** Рассуждающая модель — так ведёт себя целый класс
   моделей — порой оставляет `content` пустым и кладёт готовый JSON-ответ в `reasoning_content`;
   AI SDK такой ответ разобрать не может. На нестриминговом пути адаптер это замечает и
   копирует `reasoning_content` в `content`.

3. **Сторож зависаний + ограничитель вывода.** Один вызов может уйти в спираль или повиснуть,
   минутами не выдавая ни токена. Каждое чтение ограничено **таймаутом неактивности**: бюджет до
   первого токена (префилл) сменяется меньшим межтокенным, как только приходит первый байт, —
   и действует это на *обоих* путях, стриминговом и нестриминговом. Зависший upstream
   обрывается (одна повторная попытка, если он завис до первого байта, иначе поток аккуратно
   завершается) вместо того, чтобы заклинить ход; `FABULA_MAX_OUTPUT_TOKENS` /
   `FABULA_CONTEXT_WINDOW` обрезают неуправляемую генерацию. Это главный принцип проекта —
   надёжность даёт система вокруг модели, а не модель, — выраженный на транспортном уровне.

4. **Декларативное управление уровнем рассуждений (опционально) + телеметрия.** Таблица в
   конфиге (`proxy/reasoning-map.json`) умеет патчить «ручки» рассуждений в запросе по паре
   модель/уровень, когда уровень задан (`X-Fabula-Reasoning` / env); уровень, не описанный для
   модели, проваливается в таблицу `*` **по каждому уровню отдельно** — добавив модели один
   уровень, вы не отменяете молча остальные. Адаптер также логирует сбросы префикса KV-кэша
   (замеренная статья расходов №1) и классифицирует переполнение контекста — включая два
   *тихих* случая: усечение промпта и слишком длинный промпт, принятый без единой жалобы. Для
   классификации нужно знать окно, и окно **спрашивается у рантайма, обслуживающего модель**,
   а не настраивается: число, вписанное в `FABULA_CONTEXT_WINDOW`, устаревает при первой же
   перезагрузке модели, а без него (обычный случай) классификация не сработала бы вовсе.
   Ставьте переменную только затем, чтобы переопределить ответ рантайма.

   Диагностический лог **ограничен по размеру**: после `FABULA_ADAPTER_LOG_MAX` (20 МБ) адаптер
   копирует его в `<path>.1` и усекает на месте — именно на месте, потому что launchd открыл этот
   файл с `O_APPEND`, и переименование оставило бы процесс писать туда, откуда никто не читает.
   Клиент, бросивший keep-alive-соединение, отмечается одной строкой, а не стектрейсом: это
   обычное событие, а этот лог — первое, что вас попросят прочитать, когда что-то висит.

5. **Контроль допуска.** Этот класс серверов рушится под конкурентным префиллом (замер ниже),
   а через один-единственный адаптер проходят все сессии, фоновые проходы и обращения к
   модели-свидетелю — поэтому он сериализует работу *инференса*
   (`FABULA_MAX_CONCURRENT_UPSTREAM`, по умолчанию 1; `0` = без лимита). Лишние запросы встают
   в очередь FIFO; стриминговый клиент в очереди получает keepalive-комментарии SSE, а раз те
   уже зафиксировали ответ, ошибка upstream уезжает событием внутри SSE-потока, а не второй
   строкой HTTP-статуса. Ожидание сверх потолка вызывающей стороны разрешается **пропуском** (fail
   open: `FABULA_ADMIT_WAIT_MAX` для молчаливого клиента, более длинный
   `FABULA_ADMIT_WAIT_MAX_STREAM` для стримингового, которого держат живым keepalive) — барьер,
   который наглухо блокирует, хуже, чем отсутствие барьера. Метаданные (`GET /v1/models` —
   проверка живости из приложения) и эмбеддинги идут мимо очереди. Замер на этом железе, четыре
   конкурентных *уникальных* тяжёлых префилла: **41.1s без сериализации против 2.4s с ней**; на
   тёплом общем префиксе барьер стоит ~0.15s (префиксы у запросов уникальные — фикстура с общим
   префиксом не измеряет ничего). Барьер ограничивает голодание; приоритеты живут слоем выше —
   фоновые проходы уступают переднему плану, а допуск ставит живой ход раньше фоновых вызовов.

6. **Замеренный бюджет простоя.** Плоский межтокенный таймаут заменён — для каждой пары
   (модель, корзина размера промпта) — бюджетом, выведенным из реально наблюдаемых
   *межтокенных пауз*. Никогда не из времени до первого токена: оно управляет другой
   величиной. У бюджета есть пол, потолок из env и холодный старт, равный плоской константе.
   `FABULA_IDLE_BASELINE=0` возвращает константу.

7. **Классификация сбросов кэша.** Телеметрия сбросов говорит, *почему* сломался префикс:
   `position-shift` (байт-в-байт то же содержимое, которое просто сдвинулось — наш собственный
   порядок вставок, и виновный нестабильный блок называется по имени), `content-break`
   (настоящее изменение) и рост/сжатие. `FABULA_CACHE_BREAK_CLASS=0` возвращает прежнюю строку.

**Чат-стриминг проходит насквозь, токен за токеном** (теперь под сторожем); буферизуются и
переписываются дополнительно только *нестриминговые* структурированные ответы. Опционально
доступен **облачный провайдер — NVIDIA** (OpenAI-совместимый) — для включаемого вручную
маршрутизатора тяжёлых шагов (см. §4).

### 1.3 Приложение — нативная обёртка Swift / WKWebView

`app/FabulaApp.swift` — нативная macOS-обёртка на **Swift + WKWebView**. Она показывает
веб-интерфейс движка в собственном окне приложения — своя иконка, никакого браузерного
обрамления, — и FABULA предстаёт самостоятельным настольным приложением, а не страницей в браузере.

### 1.4 Плагины — слой возможностей

Реальные возможности агента (веб- и файловые инструменты, оркестрация, мультимодальность,
ops, надёжность, безопасность) поставляются слоем TypeScript-**плагинов** в каталоге
`plugin/`: движок их загружает, а исполняет — **bun**. Подробности — в §2 и §3.

## 2. Плагинная модель движка

Движок находит и загружает файлы плагинов и вызывает экспортированные ими функции. Плагины
участвуют в цикле агента двумя способами:

- **Регистрация инструментов** — плагин возвращает карту `tool`; каждая запись
  (`name: tool({…})`) становится инструментом, который модель может вызвать.
- **Хуки жизненного цикла** — плагин возвращает колбэки, которые движок вызывает в
  определённых точках цикла. В этой кодовой базе используются:
  - `tool.execute.before` — осмотреть/переписать/прервать вызов инструмента до его запуска
    (выброшенное здесь исключение **прерывает** инструмент — это универсальный барьер
    безопасности и защиты от зацикливания).
  - `tool.execute.after` — осмотреть/обернуть результат инструмента (например, обернуть
    недоверенный вывод).
  - `chat.message` / `chat.params` — поправить сообщения или параметры запроса до вызова
    модели (например, схлопнуть системные сообщения, вставить курируемую память).
  - `event` — отреагировать на событие движка (простой сессии, удаление чата и т.п.).

### 1.4 Каталог провайдеров чистится при чтении

Список провайдеров и моделей приходит из внешнего реестра во время работы, и чистка брендов на этапе
сборки до него не дотягивается — замерено: собранный бандл был чист, а Settings ▸ Providers всё ещё
показывал вендора, от чьего движка FABULA форкнута. `ModelsDev.get()` переписывает только ОТОБРАЖАЕМОЕ
имя этого одного вендора (он показывается как **Zen**); идентификаторы провайдеров, URL API и имена
env-переменных намеренно не тронуты: после их переименования сохранённые учётные данные и выбор
моделей пользователя остались бы бесхозными. Настоящие вендоры моделей не переименовываются никогда — их имена называют модели,
которые пользователь реально может выбрать.

### 2.0 Навигация по коду: инструмент движка `lsp`

Два переключателя, оба в FABULA включены по умолчанию. `"lsp": true` в `fabula.config.json` запускает
подсистему языковых серверов (36 серверов; сервер TypeScript берётся из `node_modules` самого проекта),
а `MIMOCODE_EXPERIMENTAL_LSP_TOOL=1` — приложение выставляет её при старте движка — открывает модели
инструмент `lsp`. Движок считает этот инструмент экспериментальным: без env-переменной он просто не
существует. Ровно поэтому навигационная подсказка в `fabula-context` завязана на ту же переменную — она
не должна советовать инструмент, которого нет.

Операции позиционные — `goToDefinition`, `findReferences`, `hover`, `documentSymbol`,
`goToImplementation` и тройка иерархии вызовов — и принимают `file_path` + `line` + `character`.
Исключение — `workspaceSymbol`: он ищет по всему рабочему пространству по ИМЕНИ, принимает `query` без
позиции, а `file_path` — только как подсказку. Языковой сервер стартует при первом обращении к файлу,
так что в холодной сессии может не работать ни один; спрошенный в этот момент, инструмент говорит об
этом прямо, а не возвращает пустой список — «никого не спросили» и «такого символа нет» — разные ответы,
и лишь один из них означает, что символа действительно нет. По той же логике `GET /find/symbol` сначала
поднимает настроенные серверы и только потом отвечает.

### 2.1 `plugin/` и `plugin/lib/` — намеренное разделение

**Ключевое правило:** движок считает **каждую экспортированную функцию файла
`plugin/fabula-*.ts` плагином** и вызывает её. Случайный посторонний экспорт в таком файле
ломает загрузку провайдеров и моделей.

Поэтому:

- **`plugin/fabula-*.ts`** — каждый файл экспортирует **ровно одну** фабрику плагина `Fabula*`
  (например `FabulaTools`, `FabulaGraph`) и **ничего больше**.
- **`plugin/lib/*.ts`** — весь общий вспомогательный код (чистые функции). Каталог `lib/`
  движок при поиске плагинов **не** сканирует, так что помощники (маршрутизация, провайдеры,
  парсеры, защиты) живут здесь и импортируются файлами плагинов.

## 3. Плагины

Всего плагинов 40. Каждый файл экспортирует одну фабрику `Fabula*`. Таблица ниже —
представительное подмножество (всегда включённое ядро); полная актуальная карта всех плагинов
и инструментов — включая шесть выключенных по умолчанию плагинов **экономики доказательств**
(`registry`, `witness`, `daemon`, `relay`, `coordinator`, `buddy`) — живёт в
[`docs/PLUGINS.ru.md`](PLUGINS.ru.md) и генерируется по манифесту.

| Плагин (файл)              | Фабрика             | Зона ответственности |
|----------------------------|---------------------|----------------|
| `fabula-tools.ts`          | `FabulaTools`       | **Основной набор инструментов**: `web_fetch` (URL→markdown, включая PDF), `web_search` + `image_search` (через SearXNG MCP), `bash_tool` / `execute_code` (шелл и код; `execute_code` предпочитает контейнер Docker, откатывается на профиль ядра macOS, а если изоляцию запросили явно — *отказывается* работать, но не понижает её), `view` / `str_replace` / `create_file` / `note_append` (работа с файлами), `present_files`, `verify_done`, `weather_fetch`, `places_search`, `mixture_of_agents` (веер на N моделей + синтез), `session_search`, `save_skill`, `cost_report`, `batch_run`, `search_mcp_registry`, `suggest_connectors`, `recommend_LLM_apps`, `fetch_sports_data`. |
| `fabula-graph.ts`          | `FabulaGraph`       | Оркестратор **`workflow_graph`**: планировщик → ≤5 изолированных подзадач → синтез, с опциональным маршрутизатором локально→облако. Ребро между шагами — контракт: шаг, не выдавший ничего, приходит как явное отсутствие, обрезка объявляет себя сама, негодный вывод перезапускается один раз и помечается пустым; все шаги делят один открывающий блок, чтобы кэш сервера переиспользовался. `workflow_graph` — лёгкий однопроходный оркестратор; полный — собственный инструмент движка `workflow`: типизированные контракты, условная маршрутизация, циклы до сходимости. ## 4. Оркестратор workflow-graph

`fabula-graph.ts` даёт один инструмент — **`workflow_graph`** — для составных задач, с
которыми один проход справляется плохо. Его конвейер:

1. **План.** Планировщик выдаёт граф из **≤5 изолированных подзадач** с объявленными
   зависимостями.
2. **Изолированное выполнение.** Каждый шаг — **отдельный, изолированный вызов модели**,
   на входе у которого только:
   - выводы его объявленных зависимостей,
   - короткая **ролевая преамбула** и
   - маркер `STOP`.
   Шаги изолированы и не наследуют весь разговор — каждый получает ровно тот контекст,
   который ему нужен; шим рассуждений в адаптере гарантирует, что ответ окажется в
   `content` при любом режиме рассуждений модели.
3. **Параллельный веер.** Шаги выполняются **уровнями зависимостей**: независимые шаги
   одного уровня идут параллельно.
4. **Синтез.** Выводы шагов синтезируются в итоговый ответ; в конец добавляется короткая
   трасса.

**По умолчанию — локально.** Каждый шаг идёт на локальную модель
(`localhost:1235/v1`). Настройки: `FABULA_GRAPH_URL`, `FABULA_GRAPH_MODEL`,
`FABULA_GRAPH_TIMEOUT_MS`.

### 4.1 Опциональный маршрутизатор локально→облако (`FABULA_ROUTER`)

Маршрутизатор (`plugin/lib/router.ts`) включается **только вручную** и по умолчанию
**выключен** (`FABULA_ROUTER=0`). Когда он включён (`FABULA_ROUTER=1`) **и** настроен облачный
провайдер, маршрутизатор оценивает каждый шаг (например, через `FABULA_ROUTER_HEAVY_CHARS`) и
**отдаёт «тяжёлые» шаги облачной модели**, оставляя лёгкие локальными. Нет облачного
провайдера — всё остаётся локальным. Итоговая трасса отмечает, был ли маршрутизатор включён.

## 5. Сквозные механизмы

Это не инструменты, а механика, пронизывающая *все* инструменты; реализована в основном
через хуки жизненного цикла.

- **Надёжность** (`fabula-reliability.ts`): **защита от зацикливания** распознаёт повторные
  вызовы без прогресса и провалившиеся вызовы и **жёстко прерывает** их исключением в
  `tool.execute.before`. Рекомендательный стоп-сигнал может проигнорировать любая модель —
  а модель здесь сменный модуль, — поэтому защита делает остановку детерминированной.
  Плюс **починка аргументов инструментов**, push-уведомления **ntfy** о простое и ошибках и
  опциональные ролевые преамбулы для actor-субагентов (`FABULA_SOULS=1`).

- **Безопасность** (`fabula-security.ts`): **защита от SSRF** на исходящих запросах,
  **маскирование секретов**, **оборачивание недоверенных результатов** в `tool.execute.after`
  (вывод инструмента — данные, а не инструкции: защита от prompt-инъекций) и барьеры
  команд/подтверждений в `tool.execute.before`. Плагин передачи состояния дополнительно
  **проверяет на угрозы и ограничивает по размеру** сохраняемые артефакты.

- **Ops** (`fabula-ops.ts`): **планирование задач**, переживающее перезапуски, — через macOS
  **launchd** (`schedule_task` / `list_scheduled` / `cancel_scheduled`), **журнал запусков**
  с обнаружением просрочки и нативные **уведомления**.

## 6. Конфигурация и требования

### Конфигурация

- Скопируйте **`fabula.config.example.json` → `fabula.config.json`** (связка движка, моделей, MCP и плагинов).
- Скопируйте **`.env.example` → `.env`** и заполните.
- **Секреты живут только в `.env` / `*.key`** (оба в gitignore) — никогда в закоммиченном конфиге.
- Ключевые переменные окружения — семейство **`FABULA_*`**, задокументированное в `.env.example`, например:
  `FABULA_ROUTER`, `FABULA_ROUTER_HEAVY_CHARS`, `FABULA_GRAPH_URL`, `FABULA_GRAPH_MODEL`,
  `FABULA_GRAPH_TIMEOUT_MS`, `FABULA_SOULS`, `FABULA_NTFY_TOPIC` / `FABULA_NTFY_URL`,
  `FABULA_VISION_*`, `FABULA_PIPER_*`, `FABULA_WHISPER_PYTHON`, `FABULA_CODE_SANDBOX`,
  `FABULA_MOA_ENDPOINTS`, `FABULA_SKILLS_DIR`.

### Требования

- **macOS**
- **CLI движка** (`fabula` — собирается скриптом `build.sh` в `bin/fabula` внутри репозитория; `setup.sh` ставит обёртку `fabula`, которая его запускает)
- **LM Studio** (локальные модели) **+ адаптер `:1235`** (`proxy/lmstudio-adapter.py`)
- **bun** — для запуска TypeScript-плагинов
- *Опционально:* **Docker** — песочница для выполнения кода
- *Опционально:* **Python** — адаптер и часть MCP-серверов
- *Опционально:* экземпляр **SearXNG** — для `web_search` / `image_search`
- *Опционально:* **облачный провайдер (NVIDIA)** — только для опционального маршрутизатора тяжёлых шагов
