## 压轴的那次运行：本地跑的模型解决了一个真实的 SWE-bench Pro 任务

**环境。** 任务出自 [SWE-bench Pro](https://github.com/scaleapi/SWE-bench_Pro-os)，跑在 qutebrowser 代码库上（实例 `479aa075…`）：一个真实的上游缺陷，成绩由*隐藏的*验收测试判定——`fail_to_pass` 必须翻绿，`pass_to_pass` 不能出现回归。模型是 **Qwen3.6-35B-A3B（量化版），在一台 MacBook Pro 上用 LM Studio 本地跑**：没有云，整条链路上任何一环都没有前沿模型。跑的是 FABULA 这套框架，验证门禁全部开着。

**这套系统一步一步逼着它做了什么：**

1. **先复现。** 动手改代码之前，框架先要一个能复现问题的测试。模型只看 issue 文本，自己写出了复现。这个复现要过双重验证才算数：在有缺陷的代码上必须失败，在参考修复上必须通过——而参考修复从头到尾没给智能体看过，它只存在于评分器里。
2. **在实时验证循环里修。** 每调用一次 `verify`，仓库真实的测试集就跑一遍；模型盯着真正的红色输出一轮轮改，而不是凭自己对 diff 的判断收工。
3. **绿了才算完成。** 验证通过，这次运行才结束。

**结果：隐藏的验收测试集 100% 通过**——每一个 fail_to_pass 都翻绿，每一个 pass_to_pass 都守住了：

| 检查项 | 得分 |
|---|---|
| fail_to_pass | **2/2** |
| pass_to_pass | **9/9** |
| 判定 | **RESOLVED** |

模型并没有变聪明。是这套系统不许「完成」在没有证明的情况下发生。

## 我们主张什么，不主张什么

- 我们**不会**把一个汇总的解决率当成承诺发出去。智能体能干多少活，随任务、模型、预算剧烈波动；一个百分比，背后没有可重放的凭证，恰恰就是本项目要终结的那类说法——没人验证过。
- 我们**确实**主张这套机制，而且它在本仓库里能直接 grep 出来：验证由系统强制执行（引擎的会话验证门禁 `session/verify-gate.ts`，默认开启；[reproduce-gate](../plugin/fabula-reproduce-gate.ts)；[change-quiz](../plugin/fabula-change-quiz.ts)；循环硬性中止）。一次运行没过检查，就是*没完成*。
- 基准测试的工具链（任务运行器、Docker 在环验证、评测脚本）正在做成可重放的凭证，好让任何第三方一条命令就能把交付出去的产物重新验证一遍。路线图上写的是这个里程碑，不是一个更大的数字。

## 一份公开的凭证，可以自己重放

第一份公开的 Proof of Done 放在 [`docs/receipts/`](receipts/)：SWE-bench Pro 实例 `e64622cd`（qutebrowser，`signal_name` 在不同 PyQt 版本之间的差异），同样是本地跑的那个模型在这套框架里解决的，成绩由该基准测试隐藏的验收测试集判定：**fail_to_pass 100%（4/4），零回归（41/43 通过，另有 2 个预期内的 xfail）——RESOLVED**。一条命令就能在你自己的机器上重放：[`bash replay.sh`](receipts/swe-bench-pro-e64622cd/replay.sh)（需要 Docker；产物、测试、判定，你都可以自己重跑一遍）。

**上面那次压轴运行为什么在这里没有凭证：** `479aa075` 跑在自动签发之前，后来一次批量运行把它的补丁覆盖掉了——现在签发之所以是自动的，原因正在于此。证据不在验证变绿的那一刻签下来，早晚会丢；所以现在每一次验证通过都会签一份。
