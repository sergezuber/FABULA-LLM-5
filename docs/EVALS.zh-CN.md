## 压轴运行 —— 一个本地服务的模型解决了一个真实的 SWE-bench Pro 任务

**设置。** qutebrowser 代码库上的一个 [SWE-bench Pro](https://github.com/scaleapi/SWE-bench_Pro-os) 任务
（实例 `479aa075…`）：一个真实的上游缺陷，由*隐藏*验收测试评判（`fail_to_pass` 必须翻绿，
`pass_to_pass` 不得出现回归缺陷）。模型：**Qwen3.6-35B-A3B（量化版），在一台 MacBook Pro 上通过
LM Studio 本地运行**——没有云，回路中任何位置都没有前沿模型。FABULA 外壳，验证门禁开启。

**系统一步一步强制了什么：**

1. **先复现。** 外壳要求在任何修复之前先有一个能复现问题的测试。模型*仅凭 issue 文本*写出了
   自己的复现。这个复现只有在通过双重验证之后才被接受：它在**有缺陷的代码上失败**，
   并在**参考修复上通过**——而参考修复从未展示给智能体（它只存在于评分器中）。
2. **在实时验证循环下修复。** 每一次 `verify` 调用都运行了仓库真实的测试集；模型是针对真正的失败（红）
   输出迭代的——而不是针对它自己对 diff 的看法。
3. **只有通过（绿）才算完成。** 运行在验证通过时结束。

**结果：隐藏验收测试集 100% 通过** —— 每一个 fail_to_pass 测试都翻绿，每一个 pass_to_pass 测试都保持通过：

| 检查项 | 得分 |
|---|---|
| fail_to_pass | **2/2** |
| pass_to_pass | **9/9** |
| 判定 | **RESOLVED** |

模型并没有变得更聪明。是系统拒绝让「完成」在没有证明的情况下发生。

## 我们主张什么、不主张什么

- 我们**不会**把一个汇总的解决率当作承诺发布。智能体的产出随任务、模型和预算剧烈波动；
  一个没有可重放凭证的百分比，正是本项目存在的意义所要终结的那种未经验证的声明。
- 我们**确实**主张这套机制，它在本仓库里可以 grep 到：验证由系统强制执行（引擎的会话 verify 门禁，
  `session/verify-gate.ts`，默认开启；[reproduce-gate](../plugin/fabula-reproduce-gate.ts)；
  [change-quiz](../plugin/fabula-change-quiz.ts)；循环硬性中止），而一次没有通过其检查的运行就是*未完成*。
- 基准测试工具链（任务运行器、Docker 在环验证、评测脚本）正在被产品化为可重放的凭证，
  使任何第三方都能用一条命令重新验证已交付的产物。
  那个里程碑——而不是一个更大的数字——才是路线图。

## 一份已发布、可重放的凭证

第一份公开的 Proof of Done 位于 [`docs/receipts/`](receipts/)：SWE-bench Pro 实例
`e64622cd`（qutebrowser，跨 PyQt 版本的 `signal_name`）—— 由外壳内同一个本地服务的模型解决，
由该基准测试的隐藏验收测试集评判：**fail_to_pass 100%（4/4），零回归缺陷
（41/43 通过 + 2 个预期的 xfail）—— RESOLVED**。一条命令就能在你的机器上重放它：
[`bash replay.sh`](receipts/swe-bench-pro-e64622cd/replay.sh)（Docker；产物、测试和判定
都归你自己重跑）。

**为什么上面那次压轴运行在这里没有凭证：** `479aa075` 那次运行早于自动签发，而后来的一次
批量运行覆盖掉了它的补丁——这恰恰就是现在签发要自动化的原因。没有在通过（绿）的那一刻签发的证据，
就是你终将失去的证据；每一次通过（绿）的运行都会签发一份。
